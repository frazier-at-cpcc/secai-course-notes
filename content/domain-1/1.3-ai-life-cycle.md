### Security at every stage
- The ==AI life cycle== never really ends
  - Data changes, attackers adapt, the business changes its mind
  - The life cycle is a loop: monitoring and feedback send work back to earlier stages
- Each stage has its own failure and its own control
  - A control added late cannot fix a decision made early: no runtime filter repairs a model trained on poisoned data
- ==Secure by design==: security requirements are written at the start, alongside the business requirements

:::figure wide 1.3-ai-life-cycle.svg | The AI life cycle as a loop, with a representative security control at each stage. Feedback re-enters at data collection, where it is checked like any other data.

### Business use case and alignment
- ==Business use case==: the problem, who benefits, and how success is measured
  - "Cut tier-1 alert triage time by 40% without missing more true positives"
  - Ask first whether AI is needed at all; a rule or a SQL query may do the job with less risk
- ==Alignment with corporate objectives==
  - The project supports a stated goal and fits the organization's risk appetite and AI policy
  - An accountable owner is named; governance approves the project (objective 4.1)
- Security questions at this stage
  - What data will it touch, and what is its classification?
  - What can it do: read only, or take actions?
  - What happens when it is wrong, and who is harmed?
  - Which laws apply (privacy, sector rules, the EU AI Act risk tier)?
- Output: requirements, a risk rating, and the first threat model (objective 2.1)

### Data collection, trustworthiness, and authenticity
- ==Data collection==: gathering data from logs, tickets, vendors, public sources, or users
  - Collect only what the use case needs (minimization, objective 2.4)
  - Record provenance as you collect (objective 1.2)
- ==Trustworthiness==: can this data be relied on?
  - Accurate, complete, current, and representative of the real environment
  - Lawfully obtained: license, consent, terms of service
  - Free of known bias that would skew results
- ==Authenticity==: is the data really from the claimed source, unaltered?
  - Authenticated collection (mutual TLS, signed API requests, service accounts)
  - Hashes and signatures from the source; C2PA credentials on media
  - Scraped public data is the classic poisoning vector; anyone can edit a web page before the crawler visits
- ==Data preparation==: cleansing, verification, labeling, balancing, splitting into train, validation, and test sets (objective 1.2)
  - Labelers are a trust boundary too: check a sample of labels, and limit who can change them
  - Keep the test set sealed; data that leaks into training inflates every score

### Model development, selection, and evaluation
- ==Model development/selection==: train your own, fine-tune, or adopt a pre-trained model
- Selecting a third-party model is a supply chain decision (`LLM03:2025 Supply Chain`)
  - Check the publisher, license, model card, and known issues
  - Prefer `safetensors` over pickle-based formats, which can run code on load
  - Scan model files (for example `modelscan`), and pin the exact revision or hash
  - Verify signatures where offered (OpenSSF model signing with Sigstore)
- Development environment controls
  - Isolated training hosts, secrets out of notebooks, pinned dependencies, tracked experiments
- ==Model evaluation==: does it meet the requirements on data it has never seen?
  - Task metrics: precision, recall, false positive rate
  - Robustness: adversarial inputs, prompt injection, jailbreaks (red teaming)
  - Fairness, safety, and privacy tests (memorized secrets, PII in output)
- Make evaluation a ==gate==: below the bar, the model is not registered

```console label="Terminal"
$ MIN_SCORE=0.95 python3 train.py
evaluation: precision 0.98  recall 0.88
gate: BLOCKED (minimum 0.95)
$ python3 train.py
evaluation: precision 0.98  recall 0.88
gate: PASSED, registered 1.0.0 sha256 501133037f0d
```

### Deployment and validation
- ==Deployment==: moving the approved model into the environment where it serves requests
  - Pull from a model registry by version and pinned hash; never from a laptop or a public URL
  - Least-privilege service account, secrets from a vault, an API gateway with authentication and rate limits
  - Check the hash before loading: a pickle-based file runs code during `load`

```python label="deploy.py (excerpt)"
with open(path, "rb") as f:
    digest = hashlib.sha256(f.read()).hexdigest()
if digest != reg["sha256"]:
    sys.exit(f"REFUSED: {path} does not match"
             " registry\n"
             f"  got {digest[:12]}, "
             f"pinned {reg['sha256'][:12]}")
# load only after the hash matches
model = joblib.load(path)
```

- ==Validation==: confirm the deployed system behaves as evaluated, in its real environment
  - A golden set of known inputs must give the evaluated outputs
  - Guardrails, logging, and access controls are confirmed active
  - Shadow or canary releases compare the new model with the old one on live traffic

```console label="Terminal"
$ python3 deploy.py
validation: 25/25 golden samples match
deployed 1.0.0
$ cp untrusted/model.joblib model.joblib
$ python3 deploy.py
REFUSED: model.joblib does not match registry
  got c06d877b337f, pinned 501133037f0d
```

- Evaluation asks "is this model good enough?"; validation asks "is this the model we approved, working as approved, here?"

### Monitoring, maintenance, and feedback
- ==Monitoring and maintenance==
  - ==Drift==: live inputs stop looking like training data (data drift), or the right answer changes (concept drift)
  - Quality: precision and recall on analyst-confirmed cases, latency, error rates, cost
  - Abuse: injection attempts, extraction-style query patterns, unusual volumes (objective 2.5)
  - Maintenance: patch the serving stack, rotate keys, retrain on schedule, retire old models and delete their data

```console label="Terminal"
$ python3 monitor.py
week 1  psi 0.01  ok
week 2  psi 0.65  DRIFT: open retraining ticket
```

- `monitor.py` computes the ==population stability index== (PSI) for one input feature against the training baseline
  - A common rule of thumb: below 0.1 stable, above 0.25 a significant shift
- ==Feedback and iteration==: user ratings, analyst corrections, incident findings, and red-team results drive the next version
  - Feedback is untrusted input: an attacker who can submit feedback can try to steer retraining
  - Validate and sample feedback before it re-enters data collection

:::exam
- Match the control to the stage: provenance and authenticity checks at data collection, evaluation metrics and red teaming at evaluation, hash or signature checks at deployment, drift detection at monitoring.
- Evaluation measures the model on held-out data before release; validation confirms the deployed system matches what was approved and meets requirements in production.
- Security starts at the business use case. A question asking when to perform the first risk assessment or threat model expects the earliest stage, not deployment.
:::
