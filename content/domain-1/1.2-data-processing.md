### Why data security comes first
- A model is a compressed copy of its training data
  - Bad, stale, or tampered data becomes bad behavior, and no code review will find it
  - Retraining is the only clean fix, so a problem caught at ingest is far cheaper than one caught in production
- Three questions to answer for every dataset
  - Is it correct? (cleansing, verification)
  - Has anyone changed it? (integrity)
  - Where did it come from, and what was done to it? (provenance, lineage)
- ==Data poisoning== (planting records, or ==label flipping== on existing ones) is covered in objective 2.6
  - OWASP lists it as `LLM04:2025 Data and Model Poisoning`
  - The controls on this page are the defenses that make poisoning visible

### Data processing: cleansing and verification
- ==Data processing==: everything between the raw export and the training set
  - Collect, cleanse, verify, transform, label, balance, split, store
  - Each step is code; version it, review it, and run it the same way every time
- ==Data cleansing==: repair what can be repaired
  - Trim stray spaces, normalize case (`High ` becomes `high`), fix encodings
  - Remove ==duplicates==: a repeated alert counts twice and pulls the model toward it
  - Handle missing values: drop the row, fill a default, or flag it
- ==Data verification==: prove each record meets the rules before it is used
  - Schema checks: required fields, types, formats, allowed values
  - Range and sanity checks: a valid IP address, a timestamp in the expected window
  - Reject into a ==quarantine== with a reason; never silently drop
- The order matters
  - Cleanse first so harmless formatting does not cause rejections, then verify what is left

```python label="cleanse.py (excerpt)"
CHECKS = {  # verification rules
    "ts": ts_ok,
    "src_ip": ipaddress.ip_address,
    "rule": bool,
    "severity": SEV.__contains__,
    "label": LABELS.__contains__,
}
```

```console label="Terminal"
$ python3 cleanse.py alerts.csv clean.csv
duplicate A-1002
rejected  A-1003  bad ts
rejected  A-1004  bad src_ip
rejected  A-1005  bad rule
rejected  A-1006  bad severity
kept 12 of 16 unique rows
```

- Reading the output
  - `A-1003` used a space instead of `T` in its timestamp; `A-1004` has the octet `300`
  - `A-1006` used `urgent`, which is not in the severity list
  - A spike in rejections is itself a signal: a broken export, or someone feeding junk

### Integrity, provenance, and lineage
- ==Data integrity==: the data is complete, accurate, and unchanged since it was approved
  - Controls: cryptographic hashes, signed manifests, write-once (WORM) storage, least-privilege write access to training buckets
- ==Data provenance==: where the data came from and who handled it
  - Source system, collector account, collection date, license or consent terms
  - Answers "may we use this?" and "can we trust this?"
- ==Data lineage==: the path from source to model
  - Which inputs, which transform scripts and versions, which output, which model was trained on it
  - Lets you find every model touched by a bad dataset, and rebuild a dataset exactly
- Provenance looks backward to the origin; lineage traces every hop in between

```json label="lineage.json"
{
  "dataset": "clean.csv",
  "derived_from": ["alerts.csv"],
  "transform": "cleanse.py",
  "source": "SIEM export, tenant soc-prod",
  "collected_by": "svc-siem-export",
  "collected_at": "2026-09-14T09:00:00Z",
  "integrity": "MANIFEST (sha256)"
}
```

- A ==hash manifest== pins every file named in the lineage record
  - Below, one malicious row is relabeled `benign` after approval: a classic label-flip poisoning edit

```console label="Terminal"
$ sha256sum *.csv cleanse.py > MANIFEST
$ sha256sum -c MANIFEST
alerts.csv: OK
clean.csv: OK
cleanse.py: OK
$ sed -i '/A-1009/s/malicious/benign/' clean.csv
$ sha256sum -c MANIFEST
alerts.csv: OK
clean.csv: FAILED
cleanse.py: OK
sha256sum: WARNING: 1 computed checksum did NOT match
```

- A hash proves the file changed; it cannot say whether the original was honest
  - Protect the manifest itself: sign it, or store it where the data writers cannot write
- Standard formats for the same idea
  - Datasheets for datasets and model cards (documentation)
  - CycloneDX ML-BOM and SPDX 3.0 AI and Dataset profiles (machine-readable inventories)

### Augmentation and balancing
- ==Data augmentation==: create new training examples from existing ones
  - Images: crop, rotate, add noise; text: paraphrase, swap synonyms
  - Security data: vary the IP addresses, user names, and timestamps around a real attack pattern
  - Synthetic records must be labeled as synthetic in the lineage, and must not leak real PII
- ==Data balancing==: correct a skewed class mix
  - SOC data is lopsided: thousands of benign alerts for every true positive
  - A model that always answers "benign" scores 99% accuracy and catches nothing
- Balancing techniques

| Technique | How it works | Watch for |
|---|---|---|
| Oversampling | repeat minority rows | overfitting to copies |
| SMOTE | synthesize minority rows | unrealistic samples |
| Undersampling | drop majority rows | lost information |
| Class weights | penalize minority errors more | needs tuning |

```console label="Terminal"
$ python3 balance.py clean.csv
before: {'malicious': 3, 'benign': 9}
after:  {'benign': 9, 'malicious': 9}
```

- `balance.py` uses scikit-learn `resample(replace=True)` to oversample the malicious class
  - Balance only the training split; the test split must keep the real-world ratio, or the evaluation lies

### Data types
- The data type decides which controls are possible

:::wide
| Type | Shape | Security examples | Control notes |
|---|---|---|---|
| ==Structured data== | fixed rows and columns, a schema | SIEM tables, CSV exports, CMDB, firewall logs parsed into fields | schema checks are easy; column-level access and masking work |
| ==Semi-structured data== | self-describing keys, flexible schema | JSON API logs, cloud audit events, XML, YAML, `key=value` syslog | validate with JSON Schema; nested fields hide surprises |
| ==Unstructured data== | no schema | email bodies, tickets, chat transcripts, PDFs, screenshots, audio | hardest to classify; hides PII and planted instructions |
:::

- Unstructured data is most of what feeds a generative model or a RAG index
  - A PDF can carry white-on-white text that a human never sees but the model reads
  - Classify and scan it (DLP, PII detection) before it enters a training set or vector store
- Convert where possible
  - Parse a log line into fields once, then apply structured-data controls

:::exam
- Cleansing fixes records (dedupe, trim, normalize); verification checks them against rules and rejects what fails. A question about a duplicate row is cleansing; a question about a malformed IP is verification.
- Provenance is the origin and custody of data; lineage is the chain of transformations into a model. A hash or signed manifest is the integrity control that detects a changed training file.
- An imbalanced dataset (few malicious samples) calls for balancing or class weights. JSON logs are semi-structured, not structured.
:::
