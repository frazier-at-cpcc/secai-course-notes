### How a prompt reaches the model
- ==Prompt engineering==: shaping the input so a model gives useful, consistent output without retraining it
  - No data collection or GPUs, and a change ships in minutes; one changed word can also flip an answer
- A chat request is a list of messages, each with a role
  - The model's ==chat template== turns them into one stream of tokens with special markers
  - The model then continues that stream after the final `assistant` marker

### System prompts and user prompts
- ==System prompt==: standing instructions from whoever built the application
  - Sets the role, the rules, the allowed topics, and the output format
  - Sent with every request; the end user usually never sees it
- ==User prompt==: this turn's request and its data (an alert, a log line, a phishing email)
- Models ship with a default system prompt, used when a request sends none

```console label="Terminal"
$ ollama show --system qwen2.5:0.5b
You are Qwen, created by Alibaba Cloud. You are a helpful assistant.
```

- Same user prompt, with and without a system prompt (qwen2.5:0.5b, temperature 0)
  - `prompt.txt` is a triage alert built from a template (see Templates below)

```console label="Terminal"
$ ./ask.sh < prompt.txt
Based on the provided alert rule and the evidence, it appears that the SSH brute force attack is targeting the web01 host. The evidence shows that the attack has failed 212 times, ...
$ ./ask.sh -s "$(cat soc.txt)" < prompt.txt | jq .
{
  "severity": "high",
  "next_step": "escalate_to_administration"
}
```

```text label="soc.txt"
You are a SOC triage assistant. Reply only with JSON like {"severity": "high", "next_step": "..."}. Severity is low, medium, or high. A successful login after many failures is high.
```

- Without it: prose a SOAR playbook cannot parse, and a wrong reading of the evidence
- With it: valid JSON with the right severity; the last sentence of `soc.txt` is analyst knowledge, written down once

### System roles
- Each message in a chat API carries a role
  - `system` (developer instructions), `user` (request and data), `assistant` (model replies, or example replies you write), `tool` (results of a function the model called)
  - Some providers add a `developer` role between system and user
- ==Role prompting==: give the model a job title and context in the system prompt
  - "You are a tier 1 SOC analyst" steers vocabulary, depth, and format
  - Narrow roles beat "helpful assistant" for repeatable work
- Models are trained to favor system instructions over user instructions
  - A tendency learned in training, enforced by nothing
  - A user prompt (or a document the model reads) can still talk the model out of its rules: ==prompt injection== (Domain 2)
  - Never put secrets in a system prompt; assume it can be extracted

### Templates
- ==Prompt template==: fixed text with placeholders that code fills in for each request
  - Every alert gets the same structure, so outputs are comparable and testable
  - Store templates in Git and review changes like code
- Example: a SIEM alert's fields fill a triage template

```text label="triage.tpl"
Alert rule: {rule}
Host: {host}
Source: {src_ip}
Evidence: {failed} failures, then login as {user}
```

```console label="Terminal"
$ ./render.py triage.tpl alert.json > prompt.txt
$ cat prompt.txt
Alert rule: SSH brute force
Host: web01
Source: 203.0.113.44
Evidence: 212 failures, then login as deploy
```

- Placeholders are where untrusted text enters
  - An attacker controls a username, an email subject, a User-Agent string
  - Fence data with clear ==delimiters== and tell the model, in the system prompt, to treat it as data

### Zero-shot, one-shot, and multi-shot
- ==Zero-shot prompting==: instructions only, no examples
  - The model relies on what it learned in training
- ==One-shot prompting==: one worked example before the real input
  - Shows the exact output format
- ==Multi-shot prompting== (few-shot): several examples, ideally covering every label
  - Teaches the label boundaries, not just the format
- Test: label Linux log lines as `RECON`, `BRUTE_FORCE`, `PRIV_ESC`, or `NORMAL`
  - System prompt lists the four labels; examples go in as user and assistant turns

:::wide
| Label (assistant turn) | Example log line (user turn) |
|---|---|
| `PRIV_ESC` | `sudo: www-data : USER=root ; COMMAND=/bin/bash -i` |
| `RECON` | `nginx: 203.0.113.80 "GET /.git/config HTTP/1.1" 404` |
| `NORMAL` | `systemd[1]: Started Daily apt download activities.` |
| `BRUTE_FORCE` | `sshd[812]: Failed password for invalid user admin from 198.51.100.7` |
| `RECON` | `kernel: UFW BLOCK SRC=198.51.100.4 DPT=445 SYN` |
| `PRIV_ESC` | `pkexec: www-data: Executing command [USER=root] [COMMAND=/bin/sh]` |
| `BRUTE_FORCE` | `sshd[815]: Invalid user oracle from 198.51.100.7` |
| `NORMAL` | `sshd[930]: Accepted publickey for deploy from 10.0.4.12` |
:::

- Zero-shot sends none of these; one-shot sends only the first `BRUTE_FORCE` row; multi-shot sends all eight

```console label="Terminal"
$ L='sshd[777]: Invalid user test from 203.0.113.44'
$ ./label.sh zero "$L"
RECON
$ ./label.sh one "$L"
RECON
$ ./label.sh multi "$L"
BRUTE_FORCE
```

- Scored on 8 held-out log lines the model never saw as examples

```console label="Terminal"
$ ./score.sh zero
zero-shot: 1/8 correct
$ ./score.sh one
one-shot: 3/8 correct
$ ./score.sh multi
multi-shot: 6/8 correct
```

- Examples changed the answers more than any instruction did
  - The two multi-shot misses: a failed `su` to root came back `BRUTE_FORCE` (the word FAILED), and a cron job run as root came back `PRIV_ESC` (the word root)
  - A 0.5B model matches words; it does not reason about what the event means
- Small models also copy the last example or the most common label; balance and shuffle the examples
- Treat prompts like models: keep a labeled validation set and re-score after every prompt or model change

:::exam
- Know the three by example count: zero-shot has none, one-shot has exactly one, multi-shot (few-shot) has several. If a question says the model returns the right content in the wrong format, adding an example is the usual fix.
- The system prompt sets role, rules, and format for every request; the user prompt carries this turn's request and data. A system prompt guides behavior but is not a security boundary.
- A prompt template is fixed text with placeholders filled per request. Watch for scenarios where an attacker-controlled field lands in a template unescaped.
:::
