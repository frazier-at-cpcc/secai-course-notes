### Scripting tools, low-code, and no-code
- Three ways to build security automation, from most control to least effort
- ==Scripting tools==: Python, PowerShell, Bash, and query languages (KQL, SPL)
  - An AI assistant drafts the script or query from a plain-language request
  - The analyst still owns it: read it, test it in a lab, run it with least privilege
  - Watch for invented functions, missing error handling, and hardcoded credentials
- ==Low-code==: visual workflow builders with room for small code steps
  - SOAR playbook editors, cloud workflow services such as Azure Logic Apps (the engine behind Microsoft Sentinel playbooks), n8n
  - Many now include an "AI step" that calls a model in the middle of a flow
- ==No-code==: drag-and-drop or natural-language builders for people who do not write code
  - "When a phishing report arrives, extract the URLs, check reputation, and reply to the user"
  - Fast to build; harder to review, version, and test

| Approach | Built by | Main risk |
|---|---|---|
| Scripting | engineers | unreviewed AI-written code |
| Low-code | analysts, engineers | over-permissioned connectors |
| No-code | anyone | shadow automation nobody owns |

### Document synthesis and summarization
- ==Document synthesis and summarization==: condense or combine long text into what a reader needs
  - Incident timelines from chat, tickets, and logs
  - Shift handoff notes; threat intelligence reports turned into a list of IOCs and actions
  - Policy and audit evidence gathered into one summary for an assessor
- Risks
  - Omission: the one line that mattered is left out
  - Hallucination: details that were never in the source
  - Indirect prompt injection: instructions hidden in a document the model is asked to read
- Controls: link every statement to its source, keep the originals, and have a human approve summaries that leave the team

### Incident response ticket management
- ==Incident response ticket management== is a good fit for AI
  - Turn raw alerts into tickets, merge duplicates, enrich with asset and user data, suggest severity and routing
- Never trust model output as data until it is checked
  - Constrain the format with a JSON schema
  - Validate the result, then check every value against the source (LLM05:2025 Improper Output Handling)

:::figure wide 3.3-alert-to-ticket.svg | The model drafts; code decides. Output that fails the schema or names something the alert never contained is rejected, and high-severity actions wait for an analyst.

```python label="ticket.py (excerpt)"
def check(text):
    t = json.loads(text)           # is it JSON?
    validate(t, SCHEMA)            # right shape?
    for v in [t["host"], t["user"], *t["iocs"]]:
        if v not in ALERT:         # grounded?
            raise Ungrounded(v)
    return t
```

- Asked for a ticket in free text, qwen2.5:0.5b wrote Markdown and invented an event ID
- With the schema passed as Ollama's `format`, the same model returned valid JSON

### Change management and AI-assisted approvals
- ==Change management==: every production change is requested, assessed, approved, scheduled, and recorded
  - Standard changes are pre-approved; normal changes go to review; emergency changes are fast-tracked and reviewed after
- AI helps at each step
  - Drafts the change request and the rollback plan from the commit or ticket
  - Scores risk from blast radius, past failures, and timing
  - Checks for conflicts with other scheduled changes
- ==AI-assisted approvals==: the model recommends; a policy decides who must sign
  - Low risk, standard change: approved automatically, logged
  - High risk or production security control: a human approver, with the AI's reasoning attached
- The human approver stays accountable
  - Log the recommendation, the approver, and any override

### Automated deployment/rollback
- ==Automated deployment/rollback==: the pipeline releases a change and reverses it without waiting for a person
  - AI watches error rates, latency, and security alerts after a release and compares them with the baseline
  - A significant change triggers rollback to the last known good version, then a ticket
- Works for application code, firewall and WAF rules, detection content, and model versions
- Rehearse the rollback; an untested rollback is a second outage
  - The gates that decide when to deploy are in the next topic, AI in CI/CD

### AI agents
- An ==AI agent== plans steps and calls tools to reach a goal with little human input
  - "Contain this host": query EDR, isolate the endpoint, disable the account, open the ticket, notify the owner
  - Tools are exposed through function calling or the ==Model Context Protocol (MCP)==
- LLM06:2025 Excessive Agency is the risk: too much functionality, too many permissions, or too much autonomy
- Controls
  - Allowlist the tools; give each tool the narrowest scope (read-only where possible)
  - ==Human in the loop== for destructive or irreversible actions
  - Limits on steps, tokens, and spend per task
  - Log every tool call with its arguments for later audit

:::exam
- AI output that feeds another system must be validated (schema, allowlists, grounding checks) before it is used. Unvalidated output that triggers an action is improper output handling.
- AI-assisted approval means the model recommends and a human with authority approves high-risk changes. A choice that lets the model approve its own production changes is the distractor.
- An agent that can do more than its task needs is excessive agency; the fix is least-privilege tools and human approval for high-impact actions.
:::
