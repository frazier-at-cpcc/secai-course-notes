### CI/CD for AI systems
- ==Continuous integration and continuous deployment (CI/CD)==: every change is built, scanned, and tested automatically, then released by the pipeline
  - CI: merge small changes often; each push runs the checks
  - CD: a change that passes every gate ships without manual steps
- An AI system has more to change than code
  - Training data, model weights, prompts, retrieval sources, and dependencies
  - Each one gets a version and goes through the same pipeline
- AI also works inside the pipeline
  - Reviews pull requests, explains scanner findings, suggests fixes, writes tests
  - AI-written code goes through the same gates as human-written code

:::figure wide 3.3-model-pipeline.svg | Each gate can stop the release. A candidate model that fails a gate never replaces the one in production.

### Code scanning
- ==Code scanning== (static application security testing, SAST) reads source code for insecure patterns without running it
  - Python: `bandit`, `semgrep`; many languages: CodeQL, SonarQube
  - Runs on every pull request; high-severity findings fail the build
- AI-specific patterns to catch
  - Loading models with `pickle` (code runs on load)
  - Model output passed to `eval`, a shell, or a SQL query
  - API keys for model providers written into the code

```console label="Terminal"
$ bandit -q -f custom bad/triage.py \
  --msg-template "{line}: {test_id} {severity}"
1: B403 LOW
2: B404 LOW
4: B105 LOW
9: B301 MEDIUM
14: B602 HIGH
```

| ID | Finding |
|---|---|
| B403 / B301 | `pickle` imported / used to load data |
| B404 / B602 | `subprocess` imported / run with `shell=True` |
| B105 | hardcoded password or token string |

### Software composition analysis
- ==Software composition analysis (SCA)== lists every third-party package and matches it against vulnerability databases
  - `pip-audit`, `npm audit`, OWASP Dependency-Check, Trivy, Grype
  - Produces or reads a ==software bill of materials (SBOM)== in CycloneDX or SPDX format
- AI stacks pull in large dependency trees: ML frameworks, tokenizers, CUDA libraries, vector database clients
- Models are dependencies too (LLM03:2025 Supply Chain)
  - Pin model versions by hash; scan model files with a tool such as `modelscan`; prefer `safetensors` over pickle formats

```console label="Terminal"
$ cat bad/requirements.txt
torch==2.5.1
$ pip-audit -r bad/requirements.txt --no-deps \
  --disable-pip -f json -o sca.json
$ jq -r -f cve.jq sca.json | sort -u
torch 2.5.1 PYSEC-2025-41 fix 2.6.0
```

- `cve.jq` keeps the advisory whose aliases include CVE-2025-32434
- CVE-2025-32434: `torch.load` with `weights_only=True` could still run code from a crafted model file; fixed in 2.6.0
  - The audit found many more PyTorch advisories for 2.5.1; the jq filter shows one

### Unit testing and regression testing
- ==Unit testing==: small, fast tests of one function in isolation
  - Feature extraction, input validation, output parsers, prompt templates
- ==Regression testing==: proves that what worked before still works
  - For code: the whole test suite reruns on every change
  - For models: the candidate must score at least as well as the model in production, within a small tolerance
- A model regression can also come from new data, a library upgrade, or a prompt change

```python label="tests/test_model.py (excerpt)"
MIN_ACCURACY = 0.80   # absolute floor
MAX_DROP = 0.01       # vs the production model

def test_accuracy_threshold():
    assert CAND >= MIN_ACCURACY

def test_no_regression():
    prod = json.load(open("models/baseline.json"))
    assert CAND >= prod["accuracy"] - MAX_DROP
```

### Model testing
- ==Model testing== checks the model artifact itself before release
  - Performance on a held-out set the model never trained on: accuracy, precision, recall
  - Per-class results; a login-risk model that misses attacks is worse than one with a few false alarms
  - Bias and fairness checks, robustness to noisy or adversarial input
  - For LLMs: evaluation sets, jailbreak and prompt-injection test suites (garak, promptfoo), and hallucination checks
- In the demo, v2 was retrained after a labeling bug flipped 35% of the training labels

```console label="scikit-learn model, synthetic login data"
$ grep -E 'FAILED|passed' logs/model-tests.log
FAILED tests/test_model.py::test_no_regression - assert 0.819 >= (0.842 - 0.01)
1 failed, 1 passed in 0.22s
```

- v2 clears the 0.80 floor, so a threshold alone would ship it
- The regression test catches the 2.3-point drop against v1

### Automated deployment/rollback
- ==Automated deployment==: the last pipeline stage releases the artifact once every gate passes
- ==Automated rollback==: returns production to the last known good version
  - Before release: a failed gate leaves the current version in place
  - After release: health checks or canary metrics trigger the switch back
- Keep previous versions in an artifact store or model registry so rollback is a pointer change
- Release strategies that limit damage: canary (a small share of traffic first), blue/green (switch between two environments), shadow (new model scores live traffic, but its answers are not used)

```console label="Terminal"
$ ./pipeline.sh v1
code-scan    PASS
sca          PASS
unit-tests   PASS
model-tests  PASS
deploy       models/current -> v1.json
$ ./pipeline.sh v2
code-scan    PASS
sca          PASS
unit-tests   PASS
model-tests  FAIL
deploy       SKIPPED, prod stays v1.json
```

:::exam
- Code scanning finds flaws in your own source; software composition analysis finds known vulnerabilities in the packages and models you depend on. A scenario naming a CVE in a library points to SCA.
- A model that still meets the minimum accuracy but scores lower than the current production model fails a regression test, not a threshold test.
- Rollback depends on keeping the previous version. "Restore service fastest after a bad model release" means redeploying the last known good artifact.
:::

Run `pip-audit` against your own project's `requirements.txt`, then add `-f cyclonedx-json` to produce an SBOM from the same run.
:::
