### Data safety
- ==Data safety==: controls that keep sensitive data out of places it does not belong as it moves through an AI system
  - Prompts, training and fine-tuning sets, retrieval indexes, logs, model output
- AI raises the stakes
  - Models can memorize rare training strings and repeat them (`LLM02:2025 Sensitive Information Disclosure`)
  - A hosted model API receives everything in the prompt; its logging and retention terms now apply to your data
  - Data learned into weights is hard to remove; "unlearning" usually means retraining
- Order of operations: classify, minimize, then transform what is left
  - Apply on the way in (prompt assembly, training ingest) and on the way out (output filters, DLP on responses)

### Data classification labels
- ==Data classification labels== tag a dataset, document, or field with its sensitivity
  - A common ladder: Public, Internal, Confidential, Restricted (names vary by organization)
  - The label drives the rule: who may read it, whether it is encrypted, how long it is kept, and whether it may enter a prompt or a training set

| Label | Example fields | AI handling rule |
|---|---|---|
| Public | product docs | any approved use |
| Internal | plan names, KB articles | internal or approved models |
| Confidential | name, email, birth date | pseudonymize, mask, or drop |
| Restricted | SSN, full card number, secrets | never in a prompt or training set |

- Discovery and labeling tools: Microsoft Purview sensitivity labels, Google Cloud Sensitive Data Protection, Amazon Macie for S3
- Labels must follow the data
  - Chunks in a vector store inherit the source document's label, so retrieval can filter on it (objective 2.3)
  - A label on the file share means nothing once the file is copied into an unlabeled training bucket

```console label="Terminal (trimmed)"
$ python3 prep.py labels

email        Confidential
ssn          Restricted
card         Restricted
plan         Internal
```

### Data minimization
- ==Data minimization==: collect, keep, and send only what the stated purpose needs (GDPR Article 5(1)(c))
- In AI pipelines
  - Prompt templates pull named fields, never the whole customer object or `SELECT *`
  - Training sets drop columns that are not features; aggregated data beats raw logs when it is enough
  - RAG indexes only the libraries the assistant serves
  - Prompt and response logs get a short retention period
- Every field you drop is one less field the masking, redaction, and access controls have to get right

```console label="Terminal"
$ python3 prep.py dropped
name, email, phone, ssn, dob, zip
```

### Data masking and data redaction
- ==Data masking==: hide part of a value and keep its format
  - `**** **** **** 1111`: the agent can still say "the card ending in 1111"
  - Static masking: a masked copy of production data for dev, test, or model training
  - Dynamic masking: the database masks at query time based on the caller (SQL Server and Azure SQL dynamic data masking); stored data is unchanged
- ==Data redaction==: remove the value entirely, usually leaving a type placeholder such as `[EMAIL]`
  - Built for free text: tickets, chat transcripts, documents, logs, and model output
  - Detection uses regex, checksums (Luhn for card numbers), and named-entity models (Microsoft Presidio)
  - Detectors miss unusual formats, so redaction backs up minimization instead of replacing it

```console label="What the billing assistant receives"
$ python3 prep.py prompt
customer: cust_7d9f0c884bf5
card: **** **** **** 1111
plan: Pro
ticket:
Hi, this is [NAME] ([EMAIL],
[PHONE]). Card [CARD] was
charged twice for the Pro plan in September.
```

| Control | Value afterward | Reversible? |
|---|---|---|
| Masking | partly visible, same format | no (static) |
| Redaction | gone, placeholder left | no |
| Pseudonymization | consistent token | yes, with key or table |
| Anonymization | no link to a person | no |

### Data anonymization and pseudonymization
- ==Pseudonymization== replaces identifiers with tokens; whoever holds the key or lookup table can re-link them
  - Still personal data under GDPR (Article 4(5) defines it; Recital 26 keeps it in scope)
  - Same input, same token, so joins and per-customer analytics still work
  - Use a keyed hash (HMAC) or a secret salt; a plain hash of a guessable value is reversible by hashing guesses

```console label="Terminal"
$ python3 prep.py unkeyed
sha256 reversed by guessing: dana@example.com
$ python3 prep.py keyed
cust_7d9f0c884bf5 cust_7d9f0c884bf5
```

- ==Data anonymization== breaks the link to a person for good, against any means reasonably likely to be used
  - Anonymous data falls outside GDPR; the bar is high and is judged against linkage with other data sets
  - Techniques: drop direct identifiers, generalize (age bands, 3-digit ZIP), suppress rare records, aggregate, add calibrated noise (differential privacy)
- ==Quasi-identifiers== re-identify people in combination
  - Sweeney's classic study: ZIP code, birth date, and sex alone single out about 87% of the US population
  - HIPAA Safe Harbor removes 18 identifier types, keeps at most the first 3 ZIP digits (populous areas only), and groups ages over 89
- ==k-anonymity==: every record matches at least k-1 others on its quasi-identifiers

```console label="Terminal"
$ python3 prep.py kanon
raw (age, zip):        k = 1
banded (age, zip3):    k = 3
  30-39 282** 3
  40-49 282** 3
  50-59 282** 3
```

:::exam
- Pseudonymized data can be re-identified with the key or table and is still personal data; anonymized data cannot be. A hashed email with no secret key is pseudonymized at best.
- Masking keeps part of the value and its format (last four digits); redaction removes it; minimization means it was never sent.
- "Stop SSNs from reaching a third-party LLM" points to classification labels plus redaction or DLP at the gateway, backed by minimization in the prompt template.
:::
