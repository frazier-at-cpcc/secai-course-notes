### Encryption requirements
- Data in an AI system sits in three states, and each needs its own control
  - ==In transit==: moving between client, gateway, model, vector store, and tools
  - ==At rest==: stored in buckets, disks, databases, registries, backups
  - ==In use==: decrypted in CPU or GPU memory while a model trains or answers
- ==Encryption requirements== come from data classification and regulation
  - Which data classes must be encrypted, in which states
  - Approved algorithms and key sizes (AES-256, TLS 1.2 minimum); FIPS 140-3 validated modules for US federal work
  - Who holds the keys, how often they rotate, who may use them
  - GDPR Article 32 names encryption as an example security measure; PCI DSS requires stored card numbers to be unreadable
- AI adds assets that classic data inventories miss

| Asset | Why it is sensitive |
|---|---|
| Training and fine-tuning sets | raw customer, HR, or SOC data |
| Model weights and checkpoints | IP; a stolen copy enables white-box attacks |
| Embeddings and vector stores | inversion research recovers text from vectors |
| Prompt and response logs | whatever users pasted, plus the answers |

### In transit
- Every hop gets TLS, internal ones included
  - Browser to gateway, gateway to model server, model server to vector database, ingest jobs to SharePoint or S3, agents to tool APIs
  - TLS 1.3 preferred, TLS 1.2 minimum; TLS 1.0 and 1.1 are deprecated (RFC 8996)
- Encryption without identity checks is not enough
  - Verify the certificate chain and the hostname, or a man-in-the-middle just presents its own certificate
  - ==Mutual TLS== (mTLS): the server also verifies a client certificate, so services prove who they are to each other
- Where TLS terminates, data is plaintext again
  - Load balancers, gateways, and the model provider all see the prompt; re-encrypt behind the load balancer
- GPU-to-GPU traffic in training clusters often runs unencrypted on a dedicated fabric: isolate that fabric as its own trust zone

### At rest
:::figure wide 2.4-envelope-encryption.svg | Envelope encryption of a vector store. The sealed file carries everything needed to open it except the KEK, which stays in the KMS.

- Layers, and what each one stops

| Layer | Stops | Does not stop |
|---|---|---|
| Full disk or volume (LUKS, BitLocker, EBS) | a stolen or discarded drive | anyone logged in to the running system |
| Storage service (S3 SSE-KMS, database TDE) | raw media and backup file theft | callers allowed to read the data and use the key |
| Application or field level | storage admins, leaked backups | the application's own credentials |

- ==Envelope encryption==: a random data encryption key (==DEK==) encrypts the data; a key encryption key (==KEK==) in a KMS or HSM encrypts the DEK
  - The KEK never leaves the KMS; access to it is logged and controlled by IAM
  - Customer-managed keys let you revoke access by disabling one key
- Use ==authenticated encryption== (AEAD) such as AES-256-GCM
  - Confidentiality plus an authentication tag that detects any change
  - The 96-bit nonce must never repeat under the same key
  - Associated data (AAD) binds context, such as the index name and version, without encrypting it

```python label="vault.py (seal step)"
    dek = AESGCM.generate_key(bit_length=256)
    nonce = os.urandom(12)   # never reuse per key
    data = open(path, "rb").read()
    ct = AESGCM(dek).encrypt(nonce, data, label)
    blob = aes_key_wrap(kek, dek) + nonce + ct
```

```console label="Terminal"
$ python3 vault.py seal vectors.npy kb:v3
plaintext 307328 B, sealed 307396 B
overhead: 40 wrapped DEK + 12 nonce + 16 tag
$ python3 vault.py open vectors.npy.enc kb:v2
InvalidTag: data or label changed; refusing
$ printf X | dd of=vectors.npy.enc bs=1 seek=300 \
  conv=notrunc status=none
$ python3 vault.py open vectors.npy.enc kb:v3
InvalidTag: data or label changed; refusing
```

- The label `kb:v3` (index name and version) is the AAD: an attacker cannot swap in last month's index file
- `openssl enc` has no AEAD modes (`-aes-256-gcm` stops with `AEAD ciphers not supported`), and its CBC modes have no integrity check
  - Use a library (Python `cryptography`, Go `crypto/cipher`) or your cloud KMS SDK

### In use
- Training and inference need plaintext in memory
  - The host OS, hypervisor, cloud operator, and anyone who can dump memory can read it
- ==Confidential computing==: running the workload inside a hardware-based, attested ==trusted execution environment== (TEE)
  - The CPU encrypts and isolates TEE memory with keys the host never sees
  - ==Attestation==: the TEE presents signed measurements of its firmware and code; a KMS releases the model or data key only to a TEE that matches policy

| Technology | Protected unit |
|---|---|
| Intel SGX | an enclave inside one process |
| Intel TDX, AMD SEV-SNP | a whole confidential VM |
| Arm CCA | a realm (confidential VM) |
| NVIDIA H100 and later, CC mode | GPU work for a confidential VM |

- NVIDIA confidential mode encrypts CPU-to-GPU transfers and blocks host access to GPU memory; data inside GPU memory is not encrypted
- What a TEE does not protect
  - Bugs or malicious code inside the TEE, including a model that leaks data through its answers or obeys a prompt injection
  - Availability: the host can still stop the VM
  - Some side-channel attacks; vendors patch these through microcode and firmware updates
- Other in-use techniques: homomorphic encryption (compute on ciphertext, with large overhead) and secure multiparty computation

:::exam
- Match the state to the control: TLS or mTLS for in transit, KMS-backed AES for at rest, a TEE with attestation for in use. "Protect the prompt from the cloud operator during inference" points to confidential computing.
- Full disk encryption does nothing against an attacker using valid application credentials on a running server.
- AES-GCM gives integrity as well as confidentiality: a modified ciphertext fails to decrypt instead of returning altered data.
:::
