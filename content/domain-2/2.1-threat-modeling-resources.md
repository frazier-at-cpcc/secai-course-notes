### Threat modeling an AI system
- ==Threat modeling==: a structured look at a design to find what can go wrong before attackers do
  - Four working questions: what are we building, what can go wrong, what will we do about it, did we do a good enough job
- Start from a data flow diagram with ==trust boundaries==
  - AI adds boundaries a web app does not have: prompt assembly, retrieval from a vector store, tool calls made by the model, and the model file itself
  - Anything that reaches the prompt is a possible instruction, including a retrieved PDF
- Redo it when the agent gains a tool, RAG gains a source, or the base model changes

### Threat-modeling frameworks
- ==STRIDE== sorts threats into six categories, each the opposite of a security property
  - Works on an LLM app the same way it works on any app; the examples change

:::wide
| STRIDE | Property broken | LLM help desk app example | Control |
|---|---|---|---|
| Spoofing | Authentication | Injected text claims "I am the administrator"; agent calls a tool with a shared service key | Identity comes from the session, never the prompt; per-user tokens |
| Tampering | Integrity | Poisoned document added to the RAG index; altered model file in the registry | Signed artifacts, hashes, review before ingestion |
| Repudiation | Non-repudiation | No record of which prompt made the agent reset a password | Log prompt, retrieved sources, tool calls, and user ID |
| Information disclosure | Confidentiality | System prompt or another user's ticket appears in a reply | Permission-aware retrieval, no secrets in prompts, output filters |
| Denial of service | Availability | Huge prompts or loops of agent calls exhaust GPU time and budget | Rate limits, token caps, quotas, timeouts |
| Elevation of privilege | Authorization | Prompt injection makes the agent use admin tools for a basic user | Least-privilege tools, human approval for high-impact actions |
:::

- AI-specific frameworks add layers STRIDE does not name
- ==MAESTRO== (Multi-Agent Environment, Security, Threat, Risk, and Outcome): Cloud Security Alliance, February 2025, built for agentic AI
- Its seven layers
  - Foundation models; data operations; agent frameworks; deployment and infrastructure; evaluation and observability; security and compliance (a vertical layer across the others); the agent ecosystem
- Its method: split the system into those layers, list threats per layer, then look for threats that cross layers
  - A poisoned document in data operations drives a tool call in the agent framework
- Pair a framework with the lists: STRIDE or MAESTRO finds threats in your design; OWASP and ATLAS name them and suggest controls

### MITRE ATLAS
- ==MITRE ATLAS==: MITRE Adversarial Threat Landscape for Artificial-Intelligence Systems (ATLAS), at atlas.mitre.org
  - A knowledge base of attacker ==tactics== (the goal), ==techniques== (how), mitigations, and case studies of real and red-team attacks on AI
  - Modeled on MITRE ATT&CK; many tactics share ATT&CK names, plus AI-only ones such as ==AI Model Access== and AI Attack Adaptation
- ID formats
  - Tactic `AML.TA0005` (Execution), technique `AML.T0051` (LLM Prompt Injection), sub-technique `AML.T0051.001` (Indirect), mitigation `AML.M0020` (Generative AI Guardrails), case study `AML.CS0000`
- Released as data on GitHub (`mitre-atlas/atlas-data`), so it can be queried and mapped to detections

- ATLAS answers "how would an attacker do it, step by step, and what has worked before"
  - Case studies feed red-team plans and tabletop exercises; mapping SOC detections to technique IDs shows gaps
- Counts change with monthly releases; learn the structure, not the numbers

### MIT AI Risk Repository
- ==MIT AI Risk Repository==: the Massachusetts Institute of Technology (MIT) AI Risk Repository at airisk.mit.edu, a free database of more than 1,600 AI risks pulled from 65 published frameworks and reviews, from MIT FutureTech
  - Shared as a spreadsheet under CC BY 4.0; filter it instead of reading it
- Two taxonomies classify every risk
  - ==Causal taxonomy==: entity (human or AI), intent (intentional or unintentional), and timing (pre-deployment or post-deployment), each with an "other" option
  - ==Domain taxonomy==: 7 domains split into 24 subdomains:
    (1) discrimination and toxicity, (2) privacy and security, (3) misinformation, (4) malicious actors, (5) human-computer interaction, (6) socioeconomic and environmental, (7) AI system safety, failures, and limitations
- Answers "what harms could this system cause, to whom, and when"
  - Wider than security: bias, overreliance, and environmental cost appear next to attacks
  - Good input for a risk register and an AI impact assessment

### CVE AI Working Group
- ==Common Vulnerabilities and Exposures (CVE)==: the program that assigns an ID in the form `CVE-<year>-<number>` to each publicly known vulnerability in a product
- The Common Vulnerabilities and Exposures (CVE) AI Working Group, or ==CVE AI Working Group== (CVEAI WG), works out where AI issues fit in CVE
  - Set up after the program's July 2024 blog on AI-related vulnerabilities; open to CVE Numbering Authorities (CNAs) and to AI security practitioners
  - Its goal: define which AI problems belong in CVE, and point the rest to other AI risk efforts
- Direction published by the program so far (still described as pre-decisional)
  - Most AI vulnerabilities are ordinary software vulnerabilities in the system around the model, and get CVEs the usual way
  - A prompt injection that only slips past a filter is usually a detection bypass, not a CVE; one that triggers another weakness (data exposure, code execution) usually is
  - Bias, wrong answers, and harmful content that a guardrail misses are generally not CVE material
  - New CWE entries for AI: ==CWE-1426== (Improper Validation of Generative AI Output) and ==CWE-1427== (Improper Neutralization of Input Used for LLM Prompting)
- Answers "is there a known vulnerability in a product we run": watch CVEs for the inference server, frameworks, and plugins in the AI bill of materials

### Which resource answers which question
- Scenario: the team is launching a RAG help desk assistant that can reset passwords through a tool
  - Each resource answers a different question; the ==threat model== and the ==risk register== cite several

:::wide
| Question the team asks | Resource |
|---|---|
| What are the most common risks for an LLM app like this? | OWASP Top 10 for LLM Applications (2025) |
| Our fraud model is a classifier, not an LLM; what applies? | OWASP Machine Learning Security Top 10 |
| What can go wrong at each boundary in our design? | STRIDE on the data flow diagram |
| The assistant uses tools and other agents; what threats cross layers? | MAESTRO |
| How would an attacker chain steps, and which mitigations map to them? | MITRE ATLAS |
| What non-security harms (bias, overreliance) should the risk register list? | MIT AI Risk Repository |
| Does the inference server or plugin we use have a published vulnerability? | CVE (with CWE-1426 and 1427 for AI weakness types) |
:::

:::exam
- Match the resource to the question: ATLAS for attacker tactics and techniques, OWASP for ranked application risks, the MIT repository for a broad catalog of AI harms, CVE for specific vulnerabilities in specific products.
- STRIDE still works for AI: injection that grants admin tools is elevation of privilege; a missing record of agent actions is repudiation.
- A guardrail bypass with no further impact is usually not given a CVE ID; a prompt injection that leads to code execution or data exposure can be.
:::
