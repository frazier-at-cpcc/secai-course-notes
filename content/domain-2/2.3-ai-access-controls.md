### Four doors into an AI system
- An AI deployment has more entry points than a classic web app
  - ==Model access==: who may invoke, tune, download, or replace a model
  - ==Data access==: who may read training sets, retrieval stores, prompts, and logs
  - ==Agent access==: what an agent may do with tools on a user's behalf
  - ==Network/API access==: which networks and clients can reach an endpoint at all
- ==Least privilege== applies to every identity, human or not
  - Users, ==service identities== (managed identities, workload identities, IAM roles), agents, CI pipelines
  - Each workload gets its own identity; never one shared admin key for "the AI"
- Enforce authorization outside the model
  - A system prompt that says "never reset passwords" is a request; prompt injection can override it
  - A gateway check on the caller's identity cannot be talked out of its decision

:::figure wide 2.3-agent-gateway.svg | The model only proposes actions. The gateway decides, using the identity attached to the request and policy the model cannot see or change.

### Model access
- Split permissions by action on the model

| Action | Who | Risk if too broad |
|---|---|---|
| Invoke (inference) | apps, through a gateway | cost abuse, model extraction |
| Fine-tune or train | ML engineers | data and model poisoning |
| Download weights | very few | stolen IP, offline white-box attacks |
| Promote or deploy | release pipeline, with approval | swapped or backdoored model |

- ==Scoped API keys==: a key names the models and actions it allows
  - Plus a quota, a rate limit, and an expiry date
  - Store only a hash of each key server side, like a password table
  - Never ship a key in a browser app or a mobile binary; call through your own backend
- Model registry roles: anyone in the ML team may register a version; only an approver moves it to production
- Rate limits and quotas limit `LLM10:2025 Unbounded Consumption` and slow extraction by mass querying

```console label="Toy AI gateway: scoped keys"
$ curl -sX POST $GW/v1/invoke/helpdesk-chat \
  -H "Authorization: Bearer $BOT_KEY"
{"model": "helpdesk-chat", "status": "accepted"}
$ curl -sX POST $GW/v1/invoke/fraud-scorer \
  -H "Authorization: Bearer $BOT_KEY"
{"error": "missing invoke:fraud-scorer"}
$ curl -sw "%{http_code}\n" -o /dev/null \
  -X POST $GW/v1/invoke/helpdesk-chat
401
```

- ==401== means "who are you?" (no key, bad key); ==403== means "known, but not allowed"

### Data access
- AI data stores to protect: training and fine-tuning sets, evaluation sets, the RAG corpus and its ==vector store==, prompt and response logs, feature stores
- A RAG assistant can only leak what retrieval hands it
  - So retrieval must enforce the permissions of the person asking
  - Copy each source document's ACL or label into chunk metadata at ingest
  - Filter in the vector query itself, before ranking, and never rely on the model to withhold text it was given
  - Risks: `LLM02:2025 Sensitive Information Disclosure`, `LLM08:2025 Vector and Embedding Weaknesses`
- ==RBAC==: permissions attach to roles (`hr-manager`, `support-agent`)
  - Easy to audit; grows into "role explosion" as exceptions pile up
- ==ABAC==: a policy evaluates attributes of the subject, resource, action, and environment (NIST SP 800-162)
  - Department, clearance, data label, region, time of day
- ==Confused deputy==: a bot that searches with its own all-access index identity returns HR files to anyone who asks nicely
  - Search with the user's identity or attributes, not the bot's
- Prompt logs hold whatever users pasted: restrict them like the source data

```console label="Same query, different callers"
$ curl -s "$GW/v1/search?q=salary" \
  -H "Authorization: Bearer $BOT_KEY"
{"results": []}
$ curl -s "$GW/v1/search?q=salary" \
  -H "Authorization: Bearer $HR_KEY"
{"results": ["HR-310"]}
```

```python label="gateway.py (excerpt)"
# Per-agent allowlist: the bot only reads tickets
TOOLS = {"svc-helpdesk-bot": {"lookup_ticket"}}

def can_read(doc, a):
    return (doc["dept"] in ("all", a["dept"])
            and doc["level"] <= a["level"])
```

### Agent access
- An agent is a model that chooses and calls tools
  - `LLM06:2025 Excessive Agency`: too much functionality, too many permissions, or too much autonomy
- ==Tool allowlist== per agent
  - Offer the model only the tools its job needs, and enforce the same list at the tool gateway
  - Prefer narrow tools (`lookup_ticket`) over general ones (`run_sql`, `shell`, `http_get`)
  - Constrain arguments: refunds up to $50, reads only within the caller's tenant
- Delegated, short-lived credentials
  - The agent acts with the user's permissions (OAuth token exchange, on-behalf-of flows), never more
  - Tokens expire in minutes; no long-lived keys in the agent's prompt or memory
- ==Human-in-the-loop== approval for high-impact actions: payments, deletions, password resets, outbound email
- MCP servers act as OAuth 2.1 resource servers
  - Accept only tokens issued for that server (audience-bound); never pass a client's token through to another API

```console label="qwen2.5:0.5b agent, toy gateway"
$ python3 agent.py "Status of ticket INC-1042?"
model asks: lookup_ticket {"ticket_id": "INC-1042"}
gateway: 200 {"status": "open"}
$ python3 agent.py "Reset the password for jdoe."
model asks: reset_password {"user": "jdoe"}
gateway: 403 {"error": "tool not in allowlist"}
```

- The model happily proposed a tool its identity may not use
  - The deny came from policy, and the decision is in the audit log

```console label="Terminal"
$ jq -r '[.who, .action, .result] | join(" ")' audit.log
svc-helpdesk-bot invoke:fraud-scorer deny
hr-manager-01 invoke:helpdesk-chat deny
svc-helpdesk-bot tool:lookup_ticket allow
svc-helpdesk-bot tool:reset_password deny
```

### Network/API access
- Shrink who can even reach the endpoint

| Control | What it prevents |
|---|---|
| ==Private endpoint== (AWS PrivateLink, Azure Private Link, Google Private Service Connect) | model API reachable from the internet |
| Public network access disabled on the AI service | bypassing the private path |
| API gateway in front of every model | unauthenticated, unmetered, unlogged calls |
| ==Mutual TLS== between services | a rogue workload posing as the RAG service |
| Egress allowlist for agents | a browsing tool sending data to an attacker URL |
| Segmented training network | lateral movement into GPU clusters and data lakes |

- Self-hosted model servers often have no authentication of their own
  - Ollama listens on `127.0.0.1:11434` by default; setting `OLLAMA_HOST=0.0.0.0` exposes an open API to the network
  - Put any such server behind a gateway that authenticates, or keep it on loopback

:::exam
- "Least privilege for an agent" answers are narrow tools, a per-agent allowlist, delegated short-lived tokens, and human approval for destructive actions. A stronger system prompt is the distractor.
- A RAG bot that returns documents the user cannot open is a data access problem: filter retrieval by the caller's permissions (ABAC or RBAC metadata), not the bot's.
- Private endpoints and disabled public access answer "reachable from the internet"; scoped keys and quotas answer "any key can call any model."
:::
